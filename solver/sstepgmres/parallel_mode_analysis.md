# MPI并行模式分析

## 当前实现的问题

### 冗余存储模式 (Replicated Storage)

当前代码采用的模式：
```
每个进程存储：
  - 完整的 n×n 稩疏矩阵
  - 完整的 n 维向量 (b, x, r, z, V blocks)
```

这导致：
| 进程数 | 内存占用 | 通信内容 | 实际效果 |
|-------|---------|---------|---------|
| np=1 | 1份完整数据 | 无(本地操作) | 最快 |
| np=4 | 4份完整数据(冗余) | Allreduce归约 | 增加开销 |
| np=10 | 10份完整数据(冗余) | Allreduce归约 | 开销更大 |

### 测试数据

中等规模 (n=400):
```
np=1:  时间 0.15ms
np=4:  时间 0.21ms  (增加40%)
np=10: 时间 0.81ms  (增加5倍)
```

大规模 (n=100000):
```
np=1:  时间 0.27s
np=10: 时间 1.0s    (增加4倍)
```

**结论：进程越多越慢，因为冗余存储和同步开销增加**

## 正确的分布式模式

### 行分区策略 (Row-wise Partitioning)

```
假设 n=100000, np=10:
  进程0: 存储行 0-9999    (约10000行)
  进程1: 存储行 10000-19999
  ...
  进程9: 存储行 90000-99999

每个进程:
  - 矩阵: 只有本地行的非零元素
  - 向量: 只有本地分量
  - 内存: 原来的 1/10
```

### 通信模式变化

| 操作 | 冗余存储 | 分布式存储 |
|-----|---------|-----------|
| Mat-vec | 本地计算 | 需要边界交换 |
| 内积 | Allreduce | Allreduce (相同) |
| AXPY | 本地 | 本地 (相同) |
| 内存 | O(n²/np)冗余 | O(n²/np)有效 |

### 通信开销分析

**真正的分布式并行：**
- Mat-vec边界交换: O(边界点数) 约 2×√n 次 send/recv
- Allreduce: m+1 次 (与冗余模式相同)

**额外通信：**
```
对于五对角矩阵 (2D网格):
  每进程边界 ≈ 2×√(n/np) 个点
  
假设 n=100000, np=10:
  每进程: √(10000) = 100 边界点
  边界交换通信 ≈ 200 个点 × 每块s次
  
vs 当前 Allreduce:
  Allreduce数据量 ≈ (k×s + s² + 1) × 8 bytes
  k=30时: 约 900×8 = 7200 bytes
```

## 为什么之前的测试用 np=1

**错误的决定，原因：**

1. 专注验证算法收敛性，忽略并行价值
2. 大规模问题内存足够，没有意识到分布式必要性
3. 简化测试环境，避免MPI分区复杂性

**正确的做法：**

应该实现真正的分布式矩阵存储：
```cpp
// 当前 (错误):
class CSRMatrix {
    int n;            // 全局维度
    vector<int> rowptr, colidx;
    vector<double> values;
    // 所有进程都有完整的n行
};

// 正确的分布式:
class DistributedCSRMatrix {
    int n_global;     // 全局维度
    int n_local;      // 本地行数 (≈ n_global / nprocs)
    int row_start;    // 本地起始行号
    int row_end;      // 本地结束行号
    
    vector<int> rowptr, colidx;
    vector<double> values;
    // 只存储本地行的非零元素
};
```

## 当前测试的意义

虽然不是真正的分布式，但np=10测试仍有意义：

1. **验证Allreduce正确性**: 多进程下内积聚合正确
2. **验证收敛一致性**: np=1和np=10收敛结果相同 (~1.5e-9)
3. **验证通信计数**: m+1次Allreduce准确

**不验证的内容：**
- 真正的并行加速
- 分布式存储正确性
- 边界通信开销
